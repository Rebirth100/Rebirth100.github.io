一、IO 模型演进

Linux 网络编程中，处理多个客户端连接的 IO 模型经历了以下演进：

模型 特点 优点 缺点
阻塞 IO（多进程/多线程） 每个连接一个进程/线程，recv 阻塞等待 实现简单 资源浪费严重，连接数受限
非阻塞轮询 fcntl 设置非阻塞，循环 recv 检查 不阻塞 CPU 空转忙等，效率低
select IO 多路复用，单线程监听多个 FD 单线程处理多连接，跨平台 最大 1024 个 FD，每次需重置集合
poll IO 多路复用，结构体数组管理 FD 无最大连接数限制 仍需遍历所有 FD，大量空闲连接效率低
epoll 事件驱动，回调机制 高性能，百万级连接 Linux 特有

本课程重点讲解前四种模型（阻塞IO、非阻塞轮询、select、poll），epoll 为进阶内容。

二、阻塞 IO 模型

2.1 阻塞 IO 的概念

阻塞 IO 是最基础的 IO 模型。当进程调用 recv / accept 等函数时，如果没有数据可读或没有连接到来，进程会阻塞等待，直到有数据到达才返回。

阻塞 IO 的特点： - 调用 recv 时，如果没有数据，进程挂起等待 - 数据到达后，内核将数据从内核空间拷贝到用户空间，然后返回 - 在等待期间，进程不占用 CPU（被调度器挂起）

2.2 多进程阻塞模型

为了同时处理多个客户端，使用多进程模型： - 主进程 accept 等待新连接 - 每来一个客户端，fork 一个子进程专门处理该客户端的通信 - 子进程中 recv 阻塞等待该客户端的数据

2.3 多线程阻塞模型

与多进程类似，但使用线程： - 主线程 accept 等待新连接 - 每来一个客户端，pthread_create 一个子线程处理通信

2.4 阻塞模型的问题

问题 说明
资源浪费 每个连接需要一个进程/线程，大量空闲连接占用内存
连接数受限 进程/线程数有上限，无法支持大量并发连接
切换开销 多进程/多线程频繁上下文切换，CPU 开销大
多进程 vs 多线程 多进程资源浪费程度高于多线程（进程地址空间独立，开销更大）

当进程/线程无可用处理数据时，会持续处于阻塞等待状态，即便被分配 CPU 资源也不会执行实际业务动作。多进程模型的资源浪费程度高于多线程模型。

非阻塞模式下接口未收到数据时会持续执行对应函数，造成 CPU 忙等。这是从阻塞模型到 IO 多路复用的过渡方案。

四、IO 多路复用：select

4.1 select 的概念

select 是 IO 多路复用的经典实现。它允许单个线程同时监听多个文件描述符，当其中任意一个 FD 就绪（可读/可写/异常）时，select 返回，程序再处理就绪的 FD。

select 的核心思想： - 将需要监听的 FD 加入集合（fd_set） - 调用 select 阻塞等待，直到集合中有 FD 就绪 - select 返回后，遍历集合检查哪些 FD 就绪，进行处理

4.2 核心函数与宏

参数说明： - nfds：监听的最大 FD 编号 + 1（不是 FD 数量） - readfds：监听可读事件的 FD 集合（可为 NULL） - writefds：监听可写事件的 FD 集合（可为 NULL） - exceptfds：监听异常事件的 FD 集合（可为 NULL） - timeout：超时时间 - NULL：永久阻塞，直到有 FD 就绪 - 0：非阻塞，立即返回 - 具体时间：等待指定时长后超时返回

返回值： - > 0：就绪的 FD 数量 - = 0：超时 - < 0：出错

fd_set 操作宏：

fd_set 本质是一个位图，每一位代表一个文件描述符。默认大小为 1024 位（FD_SETSIZE = 1024），因此 select 最多监听 1024 个文件描述符。

4.3 select 服务器完整示例

4.4 select 的注意事项

  1. select 会修改传入的集合：调用 select 后，集合中只保留就绪的 FD。因此每次循环前需要备份集合（backup_fds = read_fds）。

  2. nfds 参数：是最大 FD 编号 + 1，不是 FD 的数量。例如监听了 fd=3、fd=5、fd=7，则 nfds = 7 + 1 = 8。

  3. 最大连接数限制：fd_set 默认大小为 1024（FD_SETSIZE），超过 1024 的 FD 无法被 select 监听。

  4. 效率问题：select 返回后需要遍历所有 FD 检查哪些就绪，当连接数很多但大部分空闲时，效率较低。

五、IO 多路复用：poll

5.1 poll 的概念

poll 是另一种 IO 多路复用机制，与 select 功能类似，但使用结构体数组来管理文件描述符，没有最大连接数限制。

poll 与 select 的对比：

对比项 select poll
管理方式 fd_set 位图 struct pollfd 结构体数组
最大连接数 1024（FD_SETSIZE） 无限制（受系统文件描述符限制）
集合是否被修改 是，每次需重置 否，events 和 revents 分离
跨平台 广泛支持 POSIX 标准支持
大量空闲连接 效率低（遍历所有FD） 效率低（仍需遍历）

5.2 核心函数与结构体

参数说明： - fds：struct pollfd 结构体数组 - nfds：数组中元素的数量 - timeout：超时时间（毫秒） - -1：永久阻塞 - 0：非阻塞，立即返回 - > 0：等待指定毫秒数后超时

返回值： - > 0：就绪的 FD 数量 - = 0：超时 - < 0：出错

struct pollfd 结构体：

常用事件标志：

事件 说明
POLLIN 有数据可读
POLLOUT 可写（发送缓冲区有空间）
POLLERR 发生错误
POLLHUP 对端挂断（连接关闭）
POLLNVAL 文件描述符无效

events 是我们设置的要监听的事件，revents 是 poll 返回时实际发生的事件。两者分离，因此 poll 不会修改我们的输入设置。

5.3 poll 服务器完整示例

5.4 poll 的注意事项

  1. events 与 revents 分离：poll 不会修改 events 字段，因此不需要每次重置。实际发生的事件在 revents 中。

  2. 移除 FD 的技巧：从 pollfd 数组中移除某个 FD 时，可以用数组最后一个元素填充被移除的位置，然后 nfds–，避免移动大量元素。

  3. 仍需遍历：poll 返回后仍需遍历所有 FD 检查 revents，大量空闲连接时效率不高。epoll 通过事件回调解决了这个问题。

六、UDP 编程

6.1 UDP 的特点

UDP（User Datagram Protocol，用户数据报协议）是一种无连接的传输层协议：

特点 说明
无连接 不需要建立连接，直接发送数据
不可靠 不保证数据到达，不保证顺序，不确认
面向报文 一次发送一个完整报文，保留报文边界
无拥塞控制 发送方不管网络状况，直接发送
头部开销小 UDP 头部仅 8 字节
支持多播/广播 支持一对多通信

UDP 就像发短信：编辑好消息直接发送，不关心对方是否在线、是否收到。TCP 像打电话：先拨号建立连接，确认对方接听后才说话。

6.2 UDP 编程流程

UDP 服务端流程

UDP 服务端不需要 listen() 和 accept()，因为没有连接的概念。绑定成功后直接接收数据即可。

UDP 客户端流程

UDP 客户端不需要 connect()，直接通过 sendto 指定目标地址发送数据。

recvfrom — 接收数据（可获取发送方地址）

  • flags：标志，通常传 0

6.6 UDP 的信号驱动 IO

UDP 只有一种 IO 模型：信号驱动 IO。因为 UDP 是无连接的，数据到达时内核可以通过信号（SIGIO）通知进程，进程在信号处理函数中读取数据。

信号驱动 IO 是进阶内容，本课程仅提及概念，未深入展开。

6.7 TCP vs UDP 对比

对比项 TCP UDP
连接性 面向连接 无连接
可靠性 可靠，保证到达和顺序 不可靠，不保证到达和顺序
传输方式 面向字节流 面向报文（保留边界）
头部大小 20~60 字节 8 字节
拥塞控制 有 无
流量控制 有（滑动窗口） 无
适用场景 文件传输、网页、邮件 直播、视频通话、DNS、游戏
编程函数 socket/bind/listen/accept/connect/send/recv socket/bind/sendto/recvfrom

当服务器有多个网卡（多个 IP 地址）时，客户端可以通过不同的 IP 地址连接服务器，从不同的网络通道接入。这非常符合实际物理场景： - 服务器可能有内网网卡和外网网卡 - 内网客户端通过内网 IP 连接，外网客户端通过外网 IP 连接 - 自定义连接信息让客户端可以灵活选择接入通道

八、面试考点汇总

8.1 IO 模型

  1. Linux 中有哪些 IO 模型？
    • 阻塞 IO、非阻塞 IO、IO 多路复用（select/poll/epoll）、信号驱动 IO、异步 IO
  2. 阻塞 IO 和非阻塞 IO 的区别？
    • 阻塞：没有数据时进程挂起等待，不占 CPU
    • 非阻塞：没有数据时立即返回 EAGAIN，需要轮询，占 CPU
  3. select、poll、epoll 的区别？
    • select：fd_set 位图，最大 1024 FD，每次需重置，跨平台
    • poll：pollfd 结构体数组，无最大限制，events/revents 分离
    • epoll：事件驱动，回调机制，高性能，Linux 特有，支持百万级连接
  4. select 的 nfds 参数为什么是最大 FD + 1？
    • select 内部遍历 0 到 nfds-1 的 FD，检查是否在集合中
    • 传最大 FD + 1 确保所有需要监听的 FD 都被检查到
  5. select 为什么每次调用前要重置 FD 集合？
    • select 返回时会修改集合，只保留就绪的 FD
    • 因此需要备份原始集合，每次循环前恢复
  6. poll 相比 select 的优势？
    • 没有 1024 最大连接数限制
    • events 和 revents 分离，不需要每次重置
    • 结构体数组管理，更灵活

8.2 UDP

  1. TCP 和 UDP 的区别？
    • TCP：面向连接、可靠、面向字节流、有拥塞控制、头部大
    • UDP：无连接、不可靠、面向报文、无拥塞控制、头部小、支持广播多播
  2. UDP 编程为什么不需要 listen 和 accept？
    • UDP 是无连接的，不需要建立连接
    • 绑定端口后直接通过 recvfrom/sendto 收发数据
  3. UDP 如何实现可靠传输？
    • 应用层实现确认机制、超时重传、序号管理
    • 例如 QUIC 协议就是基于 UDP 实现的可靠传输
  4. UDP 的适用场景？
    • 直播、视频通话、DNS 查询、在线游戏、物联网传感器数据
    • 对实时性要求高，允许少量丢包的场景

8.3 综合

  1. 多进程/多线程服务器和 IO 多路复用的区别？
    • 多进程/多线程：每个连接一个进程/线程，实现简单，但资源消耗大
    • IO 多路复用：单线程处理多连接，资源消耗小，适合高并发
  2. 什么是水平触发和边缘触发？
    • 水平触发（LT）：只要 FD 就绪就一直通知，直到数据被处理完
    • 边缘触发（ET）：只在状态变化时通知一次，需要一次性读完所有数据
    • epoll 支持两种模式，select/poll 只有水平触发
  3. 为什么非阻塞 IO 通常和 IO 多路复用配合使用？
    • 多路复用通知 FD 就绪后，用非阻塞读写确保不会因为个别 FD 阻塞整个循环
    • 避免一个慢客户端拖垮整个服务器
