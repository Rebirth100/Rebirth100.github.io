1.2 类型判断的两种方法

项目中通常先做类型校验，确认数据格式符合协议要求后再处理，避免因数据异常导致程序崩溃。

1.3 对象取值（按字段名提取）

不同类型值的获取方式

类型 获取方式 说明
字符串 node->valuestring char* 类型
整数 node->valueint int 类型
浮点数 node->valuedouble double 类型
布尔true node->type == cJSON_True 手动判断输出
布尔false node->type == cJSON_False 手动判断输出

数值类型只能判断是 Number，无法区分 int 和 double。可通过判断字符串中是否含小数点来区分，或统一用 double 处理。

1.6 通过 child/next 指针通用遍历对象

当不清楚对象内部有哪些字段时，可通过 child 和 next 指针遍历所有键值对。

CJSON 内部结构要点 - child：指向第一个子节点（对象的第一个键值对） - next：指向下一个兄弟节点 - prev：指向上一个兄弟节点 - string：键名字符串 - valuestring / valueint / valuedouble：不同类型的值

这种通用遍历方式适合写 JSON 调试工具，能把任意结构的 JSON 完整打印出来，方便查看数据全貌。

1.7 通用JSON解析工具的作用

项目开发中通常会提供一个通用 JSON 解析工具： - 把收到的任意 JSON 数据完整解析并展示 - 帮助开发者快速了解数据结构和字段含义 - 适合跨行业项目（不同行业数据格式差异大） - 有了数据全貌后再逐步消化业务逻辑

三、断网机制设计

3.1 为什么需要断网机制

物联网终端在实际运行中可能遇到： - GPS模块故障，无法定位 - 物联网卡（4G）故障或欠费，网络不通 - 信号弱，数据丢失

项目经理常问：你的远程终端如果网络不通怎么办？产品有没有断网机制？

3.2 断网缓存方案

本地数据库设计 - 使用 SQLite（适合嵌入式Linux环境） - 单片机环境则使用其提供的存储方案（Flash/EEPROM） - 保存未确认的上报数据，状态标记为 false - 收到服务器 OK 回复后，状态改为 true 或直接删除

缓存策略 - 保留最近 N 次（如100次）未确认数据 - 或保留最近时间窗口（如3小时）内的数据 - 避免数据库无限增长

3.3 故障排查流程

当发现终端长时间未上报数据时： 1. 测网卡：检查物联网卡是否正常、是否欠费 2. 测底座：检查网卡座子是否接触不良 3. 测设备：检查终端设备本身是否故障

通过本地缓存记录，可以快速定位是哪个时间段开始断网的。

四、通信安全设计

4.1 设备身份验证（IMEI）

  • IMEI：物联网卡的设备识别码，全球唯一，无法伪造
  • 服务器提前将合法 IMEI 录入数据库
  • 收到数据后先验证 IMEI，未登记的视为非法数据直接丢弃
  • 同时可用于计费控制（如车机系统年费管理）

4.2 UDPS（加密UDP）

普通 UDP 数据是明文传输，存在风险： - 被窃取（数据内容泄露） - 被篡改（数据被修改） - 被冒充（伪造设备上报）

UDPS 方案 - 在 UDP 基础上增加加密层 - 通信前通过密钥协商（类似 HTTPS 的握手） - 所有数据加密后传输，只有持有对应密钥的服务器能解密 - 可使用开源加密库实现

类似 HTTP → HTTPS 的关系，UDP → UDPS 增加了安全性。

4.3 动态串码

  • 每次通信生成独立的动态串码（如每3-5分钟更新一次）
  • 串码在通信过程中实时生成，无法从设备外壳读取
  • 即使知道设备 IMEI，没有当前动态串码也无法冒充
  • 属于移动通信本身支持的技术（码分多址等）

4.4 安全字段汇总

字段 作用 能否伪造
device_id (IMEI) 设备身份验证 难以伪造（硬件唯一）
动态串码 防冒充、防重放 无法伪造（实时生成）
UDPS加密 防窃取、防篡改 无法破解（无密钥）
消息编号 去重、防重放 需配合设备ID使用

五、UDP可靠传输机制

5.1 UDP的不可靠性

UDP 是无连接协议，发送后不保证： - 数据一定到达（可能丢失） - 数据按顺序到达（可能乱序） - 数据不重复（可能重复）

5.2 应用层可靠机制

机制一：等待确认（ACK）

机制二：超时重发

  • 每条消息发送后启动定时器
  • 超时未收到确认则重发
  • 通常重发 3~5 次
  • 防止因信号弱导致的偶发丢失

机制三：消息编号去重

  • 每条消息携带唯一 msg_id
  • 服务器收到后检查 device_id + msg_id 是否处理过
  • 已处理过则丢弃（去重），未处理则正常处理
  • 解决重发导致的重复数据问题

机制四：消息队列管理

  • 服务器端为每个设备维护消息队列
  • 按顺序处理消息
  • 可配合多线程提高处理效率
  • 保证高并发场景下数据不丢失

5.3 可靠机制对比

机制 解决的问题 实现位置
ACK确认 知道数据是否到达 客户端+服务端
超时重发 偶发丢失 客户端
消息编号 重复数据 服务端
消息队列 高并发、顺序 服务端
